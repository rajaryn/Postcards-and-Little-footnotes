
# Postcards & Little Footnotes — Architecture

## 1. Project Overview

Postcards & Little Footnotes is a lightweight Progressive Web App for capturing small moments during a trip.

A moment can contain:

* A photo
* A caption
* Both
* Neither is required

The application organizes moments chronologically inside a trip.

The primary mental model is:

```text
Trip
 └── Moments
      ├── Photo + caption
      ├── Caption only
      ├── Photo only
      └── ...
```

Days are derived from timestamps rather than stored as separate entities.

The application is intentionally not designed as a traditional photo gallery, cloud drive, or map-first application.

The core action is:

> Something happens → capture it → continue the trip.

---

## 2. Technology Stack

### Frontend

* HTML5
* CSS3
* Vanilla JavaScript
* PWA Web App Manifest
* Service Worker
* Browser APIs where appropriate

No frontend framework is required for the MVP.

### Backend

* Python (managed via `uv`)
* Flask
* Flask REST-style JSON endpoints
* Flask static file serving where appropriate

### Database

* TiDB (Sole Database)
* MySQL-compatible SQL connector (`pymysql` with TLS/SSL encryption)
* Relational schema with foreign keys and parameterized SQL queries
* Built-in connection lifecycle management with automatic reconnect on drop
* Graceful error handling: connection or query failures return friendly 503 JSON responses without leaking credentials or internal stack traces

### Image Storage

For MVP, images are stored in a private Cloudflare R2 bucket.

```text
Cloudflare R2
└── trip-moments/
    └── trips/<trip_id>/moments/<moment_id>.<extension>
```

The browser uploads images directly to R2 using a short-lived presigned PUT URL generated by Flask.

TiDB stores the R2 object key (`photo_key`), not the image binary and not a permanent public URL.

R2 credentials must remain server-side and must never be exposed to the frontend.

## 4. Core Data Model

### trips

Represents a trip created by the user.

Suggested schema:

```sql
CREATE TABLE trips (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(255) NOT NULL,
    start_date DATE NULL,
    end_date DATE NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### moments

Represents a single captured moment.

```sql
CREATE TABLE moments (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    trip_id BIGINT NOT NULL,
    caption TEXT NULL,
    photo_key VARCHAR(500) NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    latitude DECIMAL(10, 7) NULL,
    longitude DECIMAL(10, 7) NULL,

    FOREIGN KEY (trip_id) REFERENCES trips(id)
);
```

Location fields exist in the schema as optional future metadata, but location is not a primary MVP feature.

## 6. API Structure

The MVP should expose simple JSON APIs.

### Trips

```text
GET    /api/trips
POST   /api/trips
GET    /api/trips/<trip_id>
DELETE /api/trips/<trip_id>
```

### Moments

```text
GET    /api/trips/<trip_id>/moments
POST   /api/trips/<trip_id>/moments
DELETE /api/moments/<moment_id>
```

### Image Upload

Photo uploads should use direct browser-to-R2 uploads through short-lived presigned URLs.

Suggested flow:

```text
1. Frontend asks Flask for an upload URL
2. Flask generates a unique R2 object key
3. Flask returns a short-lived presigned PUT URL
4. Browser uploads the image directly to R2
5. Frontend creates the moment with the returned photo_key + optional caption
6. Flask stores the moment metadata in TiDB
```

The frontend must never receive R2 access credentials.

A moment is valid if it contains at least one of:

```text
caption
photo_key
```

An empty moment should not be created.

For displaying a private image, Flask should generate a short-lived presigned GET URL.

## 9. PWA Architecture

The application should be installable as a PWA.

Required MVP pieces:

```text
manifest.json
service-worker.js
```

The service worker should initially focus on:

* Caching static application assets
* Allowing the application shell to load reliably
* Providing a foundation for future offline functionality

True offline moment creation and synchronization can be introduced as a later feature.

Do not pretend that the application is fully offline-first until queued writes and synchronization are actually implemented.

---

## 10. Image Handling

Cloudflare R2 is the authoritative image object store for MVP.

Recommended object key:

```text
trips/<trip_id>/moments/<moment_id>.<extension>
```

Upload flow:

1. Validate the requested file type and size.
2. Generate the object key server-side.
3. Generate a short-lived presigned PUT URL.
4. Upload directly from the browser to the private R2 bucket.
5. Store only the R2 object key in TiDB.
6. Generate short-lived presigned GET URLs when the frontend needs to display images.

Never trust the original filename.

R2 credentials must remain in backend environment variables.

Images may be resized/compressed before upload if performance requires it, but this should not introduce unnecessary processing into the MVP.

## 11. Security Principles

Even for the MVP:

* Never expose database credentials to the frontend.
* Keep secrets in environment variables.
* Validate uploaded files.
* Restrict allowed image types.
* Generate server-side filenames.
* Never construct SQL queries by directly concatenating user input.
* Use parameterized SQL queries.
* Do not expose unnecessary server filesystem paths.
* Do not commit `.env` files or credentials to Git.

## 12. Current MVP Scope

### In scope

* Create a trip
* View trips
* Open a trip
* Create a moment
* Attach an optional photo
* Add an optional caption
* View moments chronologically
* Delete moments
* Basic PWA installation
* Basic static asset caching

### Explicitly out of scope for MVP

* User accounts
* Authentication
* Social profiles
* Public discovery
* Likes
* Comments
* Followers
* Maps
* AI-generated summaries
* Automatic trip videos
* Advanced image editing
* Complex permissions
* Real-time collaboration
* Advanced R2 lifecycle/processing workflows

These can be considered later.

---

## 13. Architectural Principle

Prefer the simplest implementation that correctly supports the core experience.

Do not introduce a framework, library, service, database table, abstraction, or architectural pattern unless it solves a real problem in the application.
